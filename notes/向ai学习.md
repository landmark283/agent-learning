## 解耦——把runAgent的一轮对话逻辑提到一个函数当中
为什么要这样做？
runAgent逻辑不够简练，既要处理上下文的管理，又要处理与模型的通讯，还要处理命令行界面与用户的交互。其中最核心的逻辑就是每次用户输入后进行的一轮处理，包括了工具调用循环，上下文处理。原本的agent运行大致框架如下：
```
while(true){
    //处理用户输入
    //把用户输入放到上下文当中，然后发给ai
    while(工具调用次数不超过限制){
        if(工具调用)
            //执行工具调用，并把结果加入到上下文当中，再发回给ai
            //如果工具调用错误，把错误信息返回给ai
        else 
            //没有工具调用，说明得到了结果，把模型的输出打到输出当中给用户看; break;
    }
}
```
我们把这个工具调用循环的逻辑单独拎出来，其他的内容（包括上下文处理，日志等等）可以作为一个函数，这样就实现了核心逻辑的分离。
提出来的函数就是runTask，作用就是：
```
runTask(msg,各种其他参数，有关文本处理函数（比如写日志）)

// 文本处理由传入的函数来完成
while(工具调用次数不超过限制){
    if(工具调用)
            //执行工具调用，并把结果加入到上下文当中，再发回给ai
            //如果工具调用错误，把错误信息返回给ai
    else 
            //没有工具调用，说明得到了结果 return 结果文本;
}
```
那么原来的runAgent就只需要在接受了用户输入之后调用runTask就可以了。
这样一来，我们惊喜的发现，subagent的实现就只需要去调用这里的runTask即可，对于子agent，我们只需要保存msg实例，就可以保留它所有的对话上下文。需要使用的时候，就把这个上下文丢到runTask里面就可以了。
而且多数情况，subagent只进行一轮对话，那么使用runTask来实现subagent工具就非常简单而且自然了。   子agent的输出不应该记录到主agent的记忆当中，它的日志也就不能简单的附加在主日志后（现在的解决方案是简单的抛弃子agent的所有日志，只有在工具调用中被返回的最终结论，会随着主agent的工作自然被加入到主日志当中）。

## runTask(...)参数中的函数
在ai写的代码当中，runTask有4个函数参数。使用函数参数是必须的，我们马上就会看到。
在设计上，runTask是负责进行工具调用循环的，不应该去处理具体的输入输出（比如输出到命令行，或者写日志），但是为了让用户能够看到agent运行的状态，我们当然需要进行输入输出，所以我们就引入了几个函数来辅助进行输入输出。

### askUser
在工具调用的过程中，可能需要询问用户来执行run_command（这是常见的防止模型乱搞的方法）。这里就涉及到了命令行界面输入输出的操作，并不是runTask这个函数应该处理的内容。  怎么办呢？于是我们给它传入一个函数参数askUser，负责在此处处理询问用户的行为。
### onFinal
在一次对话结束之时，应该让用户看到结果，onFinal就负责进行这一次命令行输出。
### onToolCall
这是一个钩子，在发生工具调用时调用。
### persist
每次agent向内存当中写入上下文的时候调用，主要用来写日志。
比如每次拿到模型的response，就从里面解析出文本，然后写入上下文，于此同时就会触发persist的调用，然后persist就把这些文本写入到日志文件。


## 实现子代理
实现子代理有非常重要的一步：防止子代理递归深度过深（子代理调用子代理，然后新的子代理接着调用子代理，形成循环）。那么这样我们的subagent就需要一个上下文参数，上一个agent要告诉这个子agent，使用什么client，递归深度是多少，使用什么模型等等。
而调用subagent的是runTask，所以这些参数也必须要能够在runTask当中找到。
```
runAgent                              agentDepth: 0        ← agent.ts:308（写死在 options 里）
  └─ runTask #0 的调用帧
       const { …, agentDepth } = options;                    ← agent.ts:66
       │   （这个局部常量就是"第 0 层的身份"，活在整个 runTask #0 的生命周期）
       │
       └─ tool.execute(args, { agentDepth, client, model, askUser })   ← agent.ts:163-168
            │   （对象字面量在这里【现场组装】：没人提前 new 它，用完即弃）
            │
            └─ subagent.execute(input, ctx)                  ← tools.ts:430
                 ctx.agentDepth === 0 → 守卫通过             ← tools.ts:434
                 └─ runTask #1  agentDepth: ctx.agentDepth + 1 ← tools.ts:455
                      └─ runTask #1 的局部常量 agentDepth === 1  ← agent.ts:66（新的调用帧）
                           └─ 它执行工具时又组装一个 ctx，里面是 1 …
```
值得注意的是，这里的递归深度不能用全局的变量去传递。否则会出现这样的情况：
主模型一次进行了5个subagent调用，那么这个全局变量就会被+1五次。但是实际上我们的subagent的深度是1。
