## 目标

- 说清"上下文压缩"解决什么问题、有哪几种技术路线；

---

## 概念：为什么需要它

agent 每轮对话都要把**全部历史**发给模型。历史无限增长会带来三个代价：

1. **费用**：按输入 token 计费，历史越长每轮越贵；
2. **硬上限**：上下文窗口有限（DeepSeek 128K），超过直接报 `context_length_exceeded`，agent 当场死亡；
3. **质量**：模型在超长上下文上注意力退化（"lost in the middle"，中间信息容易被忽略）。

你的 toy 和 teenycode 目前 `messages` 无限增长——这就是这个问题的温床。

## 概念：压缩技术的谱系

| 方法 | 做法 | 成本 | 信息损失 | 代表 |
|---|---|---|---|---|
| 滑动窗口 / 截断 | 丢掉最老的消息 | 零 | 大（早期需求直接丢） | 简单 agent |
| **LLM 摘要压缩** | 旧区重写成摘要 | 一次 LLM 调用 | 小（语义保留） | **DSH、Claude Code** |
| Token 级压缩 | 删掉"不重要"的 token | 一次小模型推理 | 可控 | LLMLingua |
| 分层记忆 | 核心/摘要/原始三级 | 架构成本 | 由设计决定 | DB-GPT |

核心权衡只有一个：**压缩率 × 保真度**。压缩必然丢信息，问题只是丢多少、丢哪些。对 coding agent，"早期用户需求、改过的文件、踩过的坑"是必保项。

## 概念：DSH 生产版拆解（最值得学的部分）

`dsh-compaction-basic` 的流水线（配置默认值见下）：

1. **测量**：`dsh-token-meter` 用启发式估 token（4 字符 ≈ 1 token，因为拿不到精确 tokenizer，这是务实折中）；
2. **触发阈值**：达到上下文窗口 **80%**（`thresholdRatio: 0.8`）才压——每次压缩花一次 LLM 调用，不能太频繁；
3. **先修剪工具结果**（可选 pruner）：超大的工具输出先被截断，因为工具结果是历史里的体积大户；
4. **保留尾部**：最近 **16%**（`retainRatio: 0.16`）原文不动——近期对话对当前任务最相关；
5. **摘要调用**：LLM 读旧区，按**固定结构**输出摘要（Primary Request / Key Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step）；
6. **替换**：用 `<compacted-summary>…</compacted-summary>` 替换旧区——**替换，不是追加**，所以下次请求真的变短了；
7. **兜底**：摘要没比原文短就重试；失败就保持原状继续（宁可超长，不丢任务）。

> 还有两个生产级细节，先记个名字，W5 读源码时再看：
> - **KV cache 复用**：摘要请求尽量"重放"与上一次相同的前缀（system + tools + 旧消息），让 provider 命中缓存的 prefix，省一半以上的费用；
> - **按轮次切割**：tool 消息必须紧跟在对应的 `tool_calls` 之后（API 硬性要求），所以切割边界只能在"轮次"之间，不能从中间切断。

## 动手：teenycode 最小实现

在 `src/agent.ts` 中加入以下内容（`client`/`model` 已存在）：

```ts
// ---------- 上下文压缩（gap ④） ----------
const MAX_CONTEXT_CHARS = 24000; // ≈6000 token（4 字符 ≈ 1 token 的粗估）
const KEEP_TURNS = 3;            // 保留最近几轮原文

function estimateTokens(messages: ChatCompletionMessageParam[]): number {
  // DSH token-meter 同款启发式：序列化长度 / 4
  return messages.reduce((n, m) => n + JSON.stringify(m).length / 4, 0);
}

async function maybeCompact(
  messages: ChatCompletionMessageParam[],
  client: OpenAI,
  model: string,
): Promise<boolean> {
  if (estimateTokens(messages) < MAX_CONTEXT_CHARS) return false;

  // 找每个"用户轮次"的起点（tool 结果都跟在本轮内，按 user 切不会切断配对）
  const turnStarts: number[] = [];
  for (let i = 0; i < messages.length; i++) {
    if (messages[i].role === "user") turnStarts.push(i);
  }

  // 轮数不够就不压（保护 system 与刚发生的对话）
  if (turnStarts.length <= KEEP_TURNS) return false;
  const keepFrom = turnStarts[turnStarts.length - KEEP_TURNS]; // 保留区起点

  // 被压缩区 = system 之后 ~ keepFrom 之前（整轮自洽）
  const toSummarize = messages.slice(1, keepFrom);
  const kept = messages.slice(keepFrom);

  // 压缩引擎 = 另一次 LLM 调用（不传 tools，模型只会返回文本）
  const res = await client.chat.completions.create({
    model,
    messages: [
      {
        role: "system",
        content:
          "你是对话压缩引擎。把下面的对话历史压缩成一段简短中文摘要，务必保留：用户最初的目标与需求、已完成改动（文件路径/代码要点）、报错与修复、尚未完成的事。用简洁要点，不要遗漏关键信息。",
      },
      ...toSummarize,
    ],
  });

  const summary = res.choices[0].message.content ?? "";
  if (!summary) return false;

  // 替换：system + [user: 摘要] + 保留区原文（splice 删除旧区、插入摘要）
  messages.splice(1, keepFrom - 1, {
    role: "user",
    content: `[以下为早期对话的压缩摘要]\n${summary}`,
  });
  console.log(
    styleText("gray", `(上下文已压缩：${toSummarize.length} 条消息 → 1 条摘要)\n`),
  );
  return true;
}
```

然后在**内层循环每次请求前**调用（对应 DSH 的"step-boundary 检查"）：

```ts
while (true) {
  await maybeCompact(messages, client, model);   // ← 加这一行
  const res = await client.chat.completions.create({ ... });
```

### 三个设计决策（对照 DSH）

| teenycode 简化 | 为什么简化 | DSH 对应 |
|---|---|---|
| 字符数阈值 24000 | 一个常量够用，不引入测量服务 | `ctx.tokenMeter` + 80% 窗口阈值 |
| 保留最近 3 轮 | 常数即策略 | `retainRatio: 0.16` |
| 摘要自由格式 | 够模型记住重点 | 固定 8 段结构模板 |

## 验收标准

1. 打开一个新会话，让 agent 连续完成多轮文件读写任务（累计消息足够长后）应打印 `(上下文已压缩：N 条消息 → 1 条摘要)`；
2. 压缩后**提问早期轮次里明确说过的话**（如"我最初让你把什么功能加到哪个文件"），模型应能凭摘要答出——证明摘要保真；
3. 压缩后 `messages.length` 明显下降（在代码里临时 `console.log(messages.length)` 验证）；
4. 手动跑一个超长会话到接近真实超限前，确认不再报 context 超限错误。
